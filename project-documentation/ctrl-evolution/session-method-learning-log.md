# CTRL evolution session method learning log

Status: active capture; no skill changes authorised yet

This file preserves the working methods Krish explicitly valued during the CTRL evolution session. It is an input to a separate end-of-session skills retrospective, not authority to edit the skills while product work is still under way.

## Confirmed by Krish

1. Design against rich, realistic synthetic data early. The mock customer and representative Brain made it possible to judge whether the interface could handle the intended data reality instead of approving empty visual theatre.
2. Maintain durable ledgers and a clear progress route throughout mammoth sessions. Context compaction must not erase answers, rationale, rejected routes, approval state or the exact next gate.
3. Use stack-ranked interactive intake when it can expose meaningful trade-offs quickly. A bare question often loses the nuance that makes the eventual architecture good.
4. Give each ranked question an optional notes route. Krish often has a ranking and deeper reasoning; the interface should accept both without making the richer answer compulsory.
5. Let accumulated evidence reduce questioning. The system should synthesise what is already known and ask only where a response would change the route.
6. Make diagnostic questions difficult because of the truth they expose, never because of abstract wording. The system should perform the interpretation, then ask a concrete tap-first question with an optional note.

## Correction chronology and likely cause

This chronology preserves why a reaction occurred, not only what copy or pixel changed. The causal reading remains a working interpretation until Krish confirms it at the end-of-session retrospective.

| Observed reaction | Likely underlying failure | Durable candidate |
|---|---|---|
| Questions arrived late or as ordinary prose | Process and persistence were allowed to block the human interaction | Interaction first. Persist without making the person wait for the next visible question |
| A beautiful static mock felt like something reproducible in Canva | Visual polish was presented without a working value loop or evidence behaviour | A material proof must make the system's intelligence and interaction testable, not merely visible |
| “Nothing changes without your say-so” and similar text felt like guff | Trust was narrated repeatedly instead of being demonstrated structurally | Express custody, consent and reversibility through state and controls; say it once only when it changes the decision |
| Huge editorial titles felt pompous and wasted desktop space | The interface centred its own prose rather than the leader's consequential work | Desktop should behave like an instrument; use the viewport for comparison, evidence and action |
| “Let her show you what she notices” sounded inappropriate | Anthropomorphic flourish displaced plain meaning and introduced unintended connotation | Prefer direct task language over coy personification |
| “One move has earned the session” felt arrogant | The system congratulated itself and declared value before the user experienced it | Never self-award usefulness; show the consequence and let the person decide |
| Brain Resolution risked feeling like e-learning | A useful micro-learning mechanism was promoted above the million-dollar decision it should support | Learning traces remain subordinate to consequential decision support |
| The first Claude bridge felt like a confused wrapper | A polished transport ritual carried too little resolved context and produced no useful external result | Portability must transfer a complete, human-readable working brief with no opaque resolver dependency |
| The first harder question was incomprehensible | The user was forced to perform the system's abstraction and diagnostic interpretation | The Brain interprets first, then asks one concrete question a twelve-year-old can understand |
| The improved question still felt like verbal diarrhoea | Sophistication was expressed as simultaneous labels, explanations, notes and controls | Sequence depth progressively. One question owns the frame; rationale and provenance sit one layer deeper |
| Synthetic examples felt like business horoscopes | Generic private backstory was not anchored to a real category, company or evidence condition | Test across explicit external and internal evidence depths; require expected and forbidden diagnostic claims |
| A sparse profile looked visually impressive but personally empty | Decorative imagery and theatre masked an evidence deficit | Sparse evidence must produce a precise gap, an honest question or abstention, not simulated insight |
| Real-company research risked becoming another polished persona | Public company context can feel specific while still supporting no private claim about the leader | Store company facts, public statements, bounded inferences and private personhood as different types; richer research sharpens the decision but never invents the person |
| The first G21 diagnostic passed six specialist criteria but failed comprehension | Analytical correctness hid that the richest questions still made the leader decode finance and consulting language | Make the immediate frame and one question a versioned plain-language contract; preserve evidence, uncertainty and analytical depth one layer below |
| One synthetic company could not expose the evidence-range edge cases Krish wanted to compare | A single invented biography blurred external research quality, private input depth and model confidence into one polished story | Test public-only research separately, then use matched fictional families where identity and company stay fixed while internal evidence grows |
| The human-agency concern kept returning while customers said AI was not good enough yet | Tool capability was being treated as the adoption question, when the durable capability is how a leader frames, delegates, inspects, corrects and owns consequential work | Keep purpose, standards, exceptions and the final call human-owned; use the first-and-last-ten-percent phrase only as shorthand, never a literal score |
| A word-count and punctuation rule still admitted questions that were hard to understand | Surface brevity was mistaken for comprehension while the leader still had to diagnose technical causes or unpack product language | The Brain performs the analysis. The person supplies one choice, number, threshold, yes or no, or short fact. Preserve rejected wordings as negative regressions |
| A correction could retire a whole source even when only one sentence was wrong | Evidence records and the claims inside them were treated as the same unit | Keep the source immutable, address correction to the exact claim and prove that unaffected claims retain provenance and current standing |
| A private-audience type appeared safe but could be changed without authority | A valid enum described possible labels, not who authorised a particular record to use one | Bind each private evidence record to an evidence-specific audience authority and reject any mismatch or widening |
| Three lifecycle labels looked ordered while the validator accepted the wrong record in the middle state | Named stages were mistaken for proven state behaviour | Bind initial to no lifecycle record, contradicted to the conflict only and corrected to conflict then correction, with exact-order regressions |
| The first internal-range council exposed defects in its own ruling data | Human review instructions existed in prose but the stored envelope and adjudicator did not enforce them exactly | Treat governance as product code: exact fields, criterion versions, artifact hashes, veto rules and raw adjudication must all be executable |

The recurring pattern is not “Krish wants less detail.” He rejects detail that arrives before its use, copy that announces rather than proves and intelligence that is abstract rather than specific. The product should preserve deep layers while making the immediate state devastatingly simple.

## Candidate practices to assess at the retrospective

These are observed candidates, not yet confirmed reusable standards:

- Build a representative fixture before a material UI proof and verify every visible claim against it.
- Separate synthetic proof, local implementation, production truth and founder taste gates explicitly.
- Use structurally divergent concepts and independent judges before polishing a material surface.
- Add an advisory “What Would Krish Do?” judge only when enough documented decisions exist and it contributes a distinct critique rather than simulated approval.
- Present material artifacts cold before explaining the rationale, so founder reaction remains useful evidence.
- Preserve rejected interpretations and correction history instead of rewriting the record to make the system appear prescient.
- Keep the product hierarchy singular even when the underlying system is rich: one intervention owns the frame; evidence, private adaptation and the living map support it.
- Treat browser behaviour, mobile ergonomics, failure states and audience boundaries as part of the design, not post-design QA.
- Preserve the chronology of founder dissatisfaction with a causal interpretation and a regression rule, so later teams do not repeat the surface wording while recreating the same failure.
- Test intelligence across a four by four external/internal evidence range and three lifecycle states rather than one hero profile.
- Use a durable specialist council with sealed independent rulings, owned vetoes and deterministic adjudication before founder review.
- Route historical theory just in time by criterion and trigger; never load the archive wholesale or let historical status labels regain authority.
- Classify evidence depth by decision-bearing coverage rather than URL count or page length. A verbose company website can still be sparse evidence.
- Preserve failed council runs and each judge's sealed ruling as history. Repair into a new immutable run, then rerun every criterion so one local fix cannot hide a regression.
- Hold identity, company and external evidence fixed when testing internal evidence depth. Otherwise a more impressive diagnostic cannot be attributed to better learning.
- Freeze profile-specific expected and forbidden behaviour before building oracle-free model inputs. A model must never receive the answer key it will later be judged against.

4. Propose exact changes, regression fixtures and conflicts before editing any skill.
5. Preserve current skill behaviour unless the evidence supports a deliberate replacement.
6. Apply only the changes Krish approves, then run the relevant skill-creation, harness and verification gates.
