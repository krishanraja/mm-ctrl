# CTRL evolution session method learning log

Status: active capture; no skill changes authorised yet

This file preserves the working methods Krish explicitly valued during the CTRL evolution session. It is an input to a separate end-of-session skills retrospective, not authority to edit the skills while product work is still under way.

## Confirmed by Krish

1. Design against rich, realistic synthetic data early. The mock customer and representative Brain made it possible to judge whether the interface could handle the intended data reality instead of approving empty visual theatre.
2. Maintain durable ledgers and a clear progress route throughout mammoth sessions. Context compaction must not erase answers, rationale, rejected routes, approval state or the exact next gate.
3. Use stack-ranked interactive intake when it can expose meaningful trade-offs quickly. A bare question often loses the nuance that makes the eventual architecture good.
4. Give each ranked question an optional notes route. Krish often has a ranking and deeper reasoning; the interface should accept both without making the richer answer compulsory.
5. Let accumulated evidence reduce questioning. The system should synthesise what is already known and ask only where a response would change the route.
6. Make diagnostic questions difficult because of the truth they expose, never because of abstract wording. The system should perform the interpretation, then ask a concrete tap-first question with an optional note.

The recurring pattern is not “Krish wants less detail.” He rejects detail that arrives before its use, copy that announces rather than proves and intelligence that is abstract rather than specific. The product should preserve deep layers while making the immediate state devastatingly simple.

## Candidate practices to assess at the retrospective

These are observed candidates, not yet confirmed reusable standards:

- Build a representative fixture before a material UI proof and verify every visible claim against it.
- Separate synthetic proof, local implementation, production truth and founder taste gates explicitly.
- Use structurally divergent concepts and independent judges before polishing a material surface.
- Add an advisory “What Would Krish Do?” judge only when enough documented decisions exist and it contributes a distinct critique rather than simulated approval.
- Present material artifacts cold before explaining the rationale, so founder reaction remains useful evidence.
- Preserve rejected interpretations and correction history instead of rewriting the record to make the system appear prescient.
- Keep the product hierarchy singular even when the underlying system is rich: one intervention owns the frame; evidence, private adaptation and the living map support it.
- Treat browser behaviour, mobile ergonomics, failure states and audience boundaries as part of the design, not post-design QA.
- Preserve the chronology of founder dissatisfaction with a causal interpretation and a regression rule, so later teams do not repeat the surface wording while recreating the same failure.
- Test intelligence across a four by four external/internal evidence range and three lifecycle states rather than one hero profile.
- Use a durable specialist council with sealed independent rulings, owned vetoes and deterministic adjudication before founder review.
- Route historical theory just in time by criterion and trigger; never load the archive wholesale or let historical status labels regain authority.
- Classify evidence depth by decision-bearing coverage rather than URL count or page length. A verbose company website can still be sparse evidence.
- Preserve failed council runs and each judge's sealed ruling as history. Repair into a new immutable run, then rerun every criterion so one local fix cannot hide a regression.
- Hold identity, company and external evidence fixed when testing internal evidence depth. Otherwise a more impressive diagnostic cannot be attributed to better learning.
- Freeze profile-specific expected and forbidden behaviour before building oracle-free model inputs. A model must never receive the answer key it will later be judged against.
- Treat paraphrase, answerability and decision usefulness as different question gates. Passing one does not imply either of the others.
- Separate immutable fixture integrity from structural runtime safety, then attack both independently.
- Preserve judge disagreement when it reveals that two apparently similar tests measure different things.

## End-of-session gate

When Krish explicitly ends the session and asks for skills augmentation:

1. Inventory every skill used and the moments where its instructions helped, slowed, failed or required improvisation.
2. Distinguish CTRL-specific product knowledge from reusable building, briefing, design, memory and verification methods.
3. Map each confirmed learning to the narrowest owning skill. Do not inflate a general skill with project-specific doctrine.
4. Propose exact changes, regression fixtures and conflicts before editing any skill.
5. Preserve current skill behaviour unless the evidence supports a deliberate replacement.
6. Apply only the changes Krish approves, then run the relevant skill-creation, harness and verification gates.
