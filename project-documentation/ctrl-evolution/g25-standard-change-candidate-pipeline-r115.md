# G25 candidate standard-change pipeline R115

R115 closes the missing handoff between an accepted learning proposal and a candidate that can be inspected. Acceptance still does not edit the Brain. It creates an immutable request that freezes the proposal, decision and source manifest, then pins the source standard, criteria, evidence identities, evidence lines, target surfaces and verdicts.

## What now works

Compile turns the accepted scope into a versioned candidate only. Build creates a deterministic runtime body, a separate evaluation manifest and a release-closed build manifest. Check re-hashes the actual bytes, rebuilds independently and returns ten criterion-level findings rather than an aggregate score. One finding is a database-generated holdout-exclusion receipt: the database seals the held-out material, scans the actual runtime for an intersection and refuses a contaminated build without exposing the held-out answer to the runtime. A false-positive or drift proposal without an evidenced change remains `needs_evidence` instead of being promoted by optimism.

Every stage has owner identity, exact expected hashes, an idempotency key and a hidden capability. A database uniqueness rule permits only one running worker for a request stage, even when callers race with different idempotency keys. Candidate records are owner-readable but browser writes are closed. Cross-owner requests look absent, changed retries return a conflict, all seven direct RPCs reject missing capabilities, and stale source returns quickly as a product conflict rather than a retryable database failure.

## What the hosted proof established

One accepted false-positive proposal reached a checked candidate through all three live Edge Functions. Exact retries returned the same receipts. Two simultaneous Compile calls with different idempotency keys returned one 200 and one 409, with one durable compilation. The build was deterministic. The fresh Check returned ten findings and `passed`, including a sealed receipt for one held-out item and zero runtime intersections. A real drift proposal also completed Compile, Build and Check; it retained the existing criterion as `no_change` and independently proved its frozen opportunity provenance `holds`. The active standard and current criteria hashes were identical before and after. A second accepted request became stale when a newer standard appeared; Compile returned 409 and wrote no candidate. Cross-tenant reads returned zero rows across all five candidate tables and cleanup removed every synthetic user and pipeline row.

The security advisor exposed three trigger helpers with inherited direct execute grants. R115 closed those grants and read back zero ordinary-role execution. The seven remaining new advisor notices are the deliberately callable, capability-gated stage RPCs; the hosted proof called every one without the hidden capability and received seven 403 responses. No new pipeline-table performance warning remains.

The complete operator rollback then removed the three Edge routes, Edge and Vault capabilities, thirteen migration-history entries, five tables and every candidate function. Readback found zero residue. The restore operator reapplied the exact thirteen files, generated a new hidden capability without printing or persisting it, restored the three JWT-enabled routes and passed the whole hosted proof again. Production was never a target.

The hosted proof is also bound to the reviewed executable source, not merely to route names. A frozen deployment manifest pins each live `ezbr_sha256` bundle digest and the exact five-file source closure for Compile, Build and Check. Before and after every hosted exercise, the verifier inventories the live functions, downloads each deployed source closure through the management API, compares every byte count and SHA-256 with the reviewed local files, and refuses any change in function identity, bundle digest or downloaded bytes across the exercise. The restore operator runs the same gate before declaring success.

A fresh independent review found that the first frozen-source trigger only matched the false-positive evidence shape. The final gate is deliberately type-aware: false positives bind to rejected judgement lines and an exact current criterion; uncovered gaps bind to exact uncovered lines without inventing a criterion; drift binds an exact current criterion to a frozen set of applicable reviews and proves the criterion did not fire. The hosted proof now sends all three proposal types through the real database trigger, accepts uncovered and drift into immutable candidate requests, and repeats that proof after restore.

A later independent provenance review found that the first receipt still proved live behaviour and local source separately. It did not prove that the live functions had executed those exact reviewed bytes. R115 now records the opaque deployed bundle digests, downloaded runtime source identity, stable live function IDs and versions, and exact local equality in both the hosted and rollback receipts. The real rollback and restore cycle was repeated after adding this fail-closed gate.

The final review exposed one difference between cited evidence and proven absence. The accepted drift request had frozen opportunities in the database, but the immutable packet did not carry those run IDs into Compile and Check. The final implementation now transports that exact opportunity set through the whole conveyor and independently validates that the target criterion did not fire in any of those runs. It also repeats deployed-source verification after the final hosted call, closing the interval between a preflight source check and the exercised route.

One attempted generic `db push --include-all` exposed an inherited migration-baseline mismatch on the isolated project. It stopped on an existing policy conflict after ten unrelated historical migrations had been admitted. The exact empty legacy delta was identified against the production catalog, removed, and all ten history rows were reverted; readback found zero unexpected tables, functions, policies, columns, constraints or migration-history rows. R115 therefore uses only its explicit migration allowlist. The repository baseline must be reconciled before `--include-all` is safe on this target.

## Boundary

This is a candidate conveyor, not self-modifying memory. A passing Check does not authorize apply, deploy or release. It does not prove the candidate is valuable for a real leader, that the eventual owner approval experience is good, or that production is ready. Production, merge, cutover, release and legacy retirement remain closed.
