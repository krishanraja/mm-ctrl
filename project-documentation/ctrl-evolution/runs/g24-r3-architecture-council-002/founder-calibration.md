## Founder-fit assessment

- [INFERENCE] **Devastating customer simplicity: aligned in direction, not yet proven in use.** R3 adds no customer surface, keeps one visible question, makes quiet and abstention valid and binds one question, control, honest exit, disclosed effect and visible consequence into one versioned atom. This supports simplicity because the difficult work stays behind the moment of use. The later rendered-comprehension gate must still prove that the contract produces a genuinely simple experience.
- [INFERENCE] **Rich backstage intelligence: strongly aligned.** The ownership map, trusted selector, intervention approval and receipts give Krish the deep instrument the founder record asks to keep backstage. None of these objects should become navigation, a customer trust console or repeated privacy explanation.
- [INFERENCE] **Consequential million-dollar decisions: aligned, with efficacy still open.** Binding every route to an accepted decision frame and expected material effect protects the product from becoming profile completion, generic advice or activity reporting. The recorded founder evidence does not establish real decision-quality lift, continuation value or willingness to pay, so those remain later founder and pilot proof.
- [INFERENCE] **Human agency: aligned and worth protecting through every repair.** R3 separates an answer event, a rebuildable case update and any pending human-owned change. A repair must not turn an epistemic policy, lifecycle receipt or release compiler into a new machine authority over purpose, judgement, exception or the final call.
- [INFERENCE] **Specific rather than horoscope-like insight: currently under-specified at one decisive seam.** The Epistemic Integrity veto is founder-material because the current candidate names capability, sufficiency, causal standing and applicability without a trusted semantic owner. If model-authored labels can make a similar item eligible, the backstage machinery can manufacture specificity while the customer sees a confident but generic intervention.
- [INFERENCE] **Delight without theatre: directionally aligned, still an experience question.** Quiet, one immediate action and an answer-specific consequence create room for delight through relevance and relief. Badges, progress rails, celebratory completion, visible reason-code machinery or trust boilerplate would recreate recorded failure modes.
- [INFERENCE] **Durable judgement: aligned only if closure and release remain separate.** One canonical Brain, append-only answers, correction-aware invalidation and permissioned cross-decision reuse support durable judgement. A relationship state called `released` that can result from close-only acceptance weakens that durability by allowing commercial closure to masquerade as release standing.

## Bounded repair set

1. [INFERENCE] **Give epistemic meaning one existing owner.** Add one canonical, versioned `epistemic_policy_ref`, owned through the existing R1 governance system, to the controlling references, selector input, output watermark and invalidation set. It should bind source-class capability, trusted cutoff, independence when required, sufficiency, applicability, causal promotion and a current countercase result or an explicit bounded absence. Models may propose evidence and labels, but only the policy evaluation may make them selector-eligible. Missing, stale, invalid or indeterminate policy state returns `abstain_hold`.

2. [INFERENCE] **Make the five-route selector tell one truth.** Delete the undefined “typed provisional result” alternative. Invalid controlling references return exactly `abstain_hold` and create no actionable intervention. Valid references with unresolved contradictory evidence may select `enrich`, `ask` or `session` only when the resolving route passes every earlier eligibility rule and carries the contradiction forward. Any diagnostic provisional detail belongs on the non-authoritative hold receipt, not in a sixth route.

3. [INFERENCE] **Make relationship closure exact and keep Release separate.** Replace grouped pseudo-states with explicit enumerated edges. Rename the terminal engagement state `closed`, add an explicit `preparing -> closed` cancellation path with versioned authority, invalidation and receipt, and keep every pause and close edge literal. The existing R1 Release object remains the sole release owner, bound to a separate current leader acceptance for one exact projection, purpose, audience and canonical version set. No lifecycle state alone may grant or prove release authority.

[INFERENCE] These three repairs preserve all five specialist resolving tests in substance: trusted epistemic-policy and countercase handling, exact invalid-input selector behaviour, an executable lifecycle graph, pre-engagement cancellation, and close-versus-release non-inference. They also leave the four `PASS_WITH_WATCHPOINTS` verdicts intact rather than reopening product direction.

## Guardrails against overengineering

- [INFERENCE] Use one epistemic policy reference, not a second Brain, a configurable customer ontology or a family of policy consoles.
- [INFERENCE] Keep exactly five selector routes. Do not add a provisional route, confidence ladder, workflow stage or customer-visible completion model.
- [INFERENCE] Prefer one `closed` engagement terminal for both pre-engagement cancellation and post-engagement closure, with distinct versioned transition receipts, when their capability policy is identical. Add a separate terminal only if a real permission, retention or access difference requires it.
- [INFERENCE] Do not pull exact field names, numeric budgets, timeouts, retry limits, UI copy, rendered comprehension, consented capture, delivery traversal or commercial efficacy into G24.A. The frozen standard and candidate already assign those to later gates.
- [INFERENCE] Do not surface the repair machinery to the customer. Its value is that one precise question, one honest exit or quiet can be safe without explanation overhead.

## Guardrails against under-specification

- [INFERENCE] “Trusted code validates” is insufficient unless the policy that owns capability, sufficiency, applicability, causality and countercase treatment is itself current, versioned and authoritative.
- [INFERENCE] “Active or paused,” “intensive proof or continuing,” “close or release” and “hold or provisional” are not harmless shorthand at an architecture lock because each lets an implementer choose product and authority semantics.
- [INFERENCE] A release request, exact projection, purpose, audience and source-version set must be independently receipted. Relationship closure, payment, elapsed time or a leader's failure to object cannot substitute.
- [INFERENCE] A contradiction must remain visible through a resolving route or hold. Neither first arrival, copied provenance nor model confidence may make it disappear.
