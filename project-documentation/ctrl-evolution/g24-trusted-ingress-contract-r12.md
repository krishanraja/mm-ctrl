## Purpose

## Authority is one-way and issuable

`compile_release` creates a pending projection whose identity and fingerprint contain no future authority. A named leader can then use one explicit operation to commit an accepted Release request and Release-authority receipt bound one-way to the exact projection reference, version, fingerprint and payload. `use_release` consumes that authority only after current watermark checks.

A separate named-leader operation issues answer authority for one exact approved atom and one exact visibility acknowledgement. Both issuance operations resolve the current case identity and commit ordinary operation-registry results. Human authority rows no longer appear without an authorised creation path.

## Questions match the locked kernel

Only ranked choice is capped at five. Other grammars are bounded by the operation's byte limit. Visible wording, disclosures, consequences, options and non-null proposals must be trimmed, nonempty and free of control characters. Options are unique and cannot use reserved effect keys. The question and answer receipt use the same proposal type. Approval requires `ask` to map to a question atom and `session` to a session atom.

Answer proof also binds the leader authority and visibility leader to the exact current case identity and authenticated principal.

## Lifecycle evidence is owned

Current case identities, lifecycle action receipts, precondition evidence and both action-combination and transition-consumption records have closed authoritative rows. A lifecycle proof resolves the exact predecessor snapshot and requires its state to equal the catalogue's `from_state`. Every precondition member resolves to an authoritative evidence row and the catalogue. Joint action consumes both human action receipts once; single action and joint authority are each consumed by at most one transition.

## Delivery authority cannot multiply or strand

An origin names workspace, subject, exact committed operation reference, operation class, result fingerprint, result branch and provider target. The operation-result branch is unique across every possible origin and effect, so it cannot mint a fresh attempt budget under a second identifier.

If the final provider-boundary recheck fails after invocation-start was committed but before the capability was consumed, the worker appends an exact `invocation_aborted_before_provider` event. It records zero provider calls and `provider_called=false`; the tip is neither stranded nor mislabeled as provider failure or ambiguity.

The materializer recursively compares every schema-bearing R11 and R12 object, excluding only the version string. Every new or changed schema must carry an R12 version or generation fails. The operation and proof export maps and the invalidation receipt's embedded self-version are included.
