# G20 concept B: The Context Thread

**Artifact revision:** G20-CT-B-R1  
**Rendered evidence:** None. Concept document only  
**Approval state:** Proposed and unrendered  
**Downstream owner:** G20 concept synthesis, then one synthetic rendered proof if selected  
**Pending action:** Judge the spine against the G20 sanitized brief before any render or implementation

## Design task contract

**STATE OF USE:** Krish is between customer tasks on desktop or steering from mobile. He has one fragment to preserve, or one purpose for which Claude needs a small part of a customer's Brain. He needs to move quickly without wondering which customer, audience or truth state is active.

**USER + ACTION:** Krish must place one fragment into private staging, understand CTRL's receipt, send Claude only a purpose-bound selection, and bring one Claude result back as attributed staged material.

**GOVERNING RULE:** One visible custody thread follows one piece of material from CTRL to Claude and back. Every handoff states who it is for, what crosses the boundary and what does not. Nothing becomes trusted Brain memory through this surface.

**DATA TRUTH:** The proof uses only synthetic Maya Chen data, the approved Decision Bench state, the existing synthetic fixture, deterministic selection and receipt states, existing dialogs, clipboard behaviour and the read-only MCP substrate. It demonstrates the interaction, not the quality of CTRL's judgment or customer value. No current implementation source file is explicitly named in the sanitized brief, so no implementation file was inspected.

**MATERIALITY:** Material interaction concept. It changes how context moves between CTRL and an external thinking surface.

**BRAND + VOICE:** Preserve the dark, warm, instrument-like Mindmake system and icon-only shell. Mint marks a current answer or a completed safe transfer. Amber marks material that is new, changed, waiting or blocked. Visible language is plain and operational. Technical identifiers remain inside deliberate detail inspection.

**AUTHORITY:** Concept document only. No render, implementation, production connector, schema, customer data, account, feature enablement, deployment or release is authorised.

**PROOF IF SELECTED:** One synthetic self-contained interaction at 1440 by 900, 390 by 844 and 320 by 568. It must cover the full outbound and return loop, every required state, keyboard and touch operation, visible focus, 44 px targets, reduced motion, overflow, clipboard behaviour and safe failure closure.

## 1. Governing metaphor

The surface is a **continuous context thread** with a courier receipt at every change of custody.

The thread begins at the active customer's Decision Bench, passes through CTRL private staging, carries one sealed purpose-bound handoff to Claude, and returns to CTRL private staging. A single context parcel sits on the thread. It is not a file card, message bubble or prompt. It is the currently handled piece of material, with a visible source, audience and status.

The thread has four custody marks, not numbered steps:

- **Received by CTRL**
- **Held privately**
- **Available to Claude for one purpose**
- **Returned to private staging**

Only the current segment is bright. Earlier segments remain as small inspectable receipts. Future segments are a quiet line, not active controls. The thread never suggests that Claude and CTRL share one continuous memory. It shows the opposite: each boundary crossing is deliberate, limited and receipted.

The metaphor matters because the core product question is not "Where is the upload?" It is "Who has this context now, for what purpose, and what status does it have?" The thread answers that question at a glance.

## 2. First five seconds

The active Decision Bench remains visible behind the attached exchange surface. The opening view shows, in this order:

1. **Maya Chen, Aperture House** and **Private operator view** in the fixed identity band.
2. **Decision: How can Maya make her quality standard usable by the team?**
3. The current point on the thread: **Ready to receive one thing for Maya.**
4. One focused receiving plate: **Paste text or a link.** File and voice are clear alternate paths for the same ask.
5. A short boundary line: **New material stays private until you choose otherwise.**

The paste target owns focus when the surface opens. Ordinary paste is therefore one deliberate action. It creates an immediate receipt without a form, title field or confirmation ceremony.

The receiving plate is the only active work area. File and voice are alternate inputs, not a row of connectors. If either path is unavailable in the proof environment, it appears as unavailable text rather than an active control.

## 3. Sequencing and state transitions

### A. Receive

Krish pastes text or a URL, selects one file, or records one voice thought. The parcel lands on the first segment of the thread and the surface immediately replaces the input with a receipt.

The receipt answers five questions:

- **For:** Maya Chen, Aperture House
- **Received:** exact source type and time
- **Kept:** the original material in private staging
- **Understood:** only the subject, source and plain summary that the fixture can support
- **Not assumed:** no trusted claim, no customer visibility, no Brain change

The original remains inspectable in place. CTRL does not demand a title, category or memory destination before preserving it.

If ambiguity would change subject, audience, provenance or meaning, the thread stops at an amber knot. It asks one direct question with two or three plain choices. The source is already safe. Answering the question updates the receipt, not the durable Brain.

### B. Choose the job

Once the receipt is clear, one action appears beside it: **Use this in Claude**.

That action does not send the whole Brain. It advances the same parcel to a purpose mark and asks one question:

**What should Claude help with?**

The proof offers a small set of fixture-backed choices tied to the active decision, plus **Name another job** as a short text fallback. Nothing is preselected. For the representative route, the named purpose is to prepare work on how Maya can make her quality standard usable by the team.

CTRL then drafts the smallest context selection the synthetic fixture can support for that purpose. Selection quality is not claimed. In the proof, the proposed set is deterministic and fixture-backed.

### C. Inspect the handoff

The parcel opens into a compact packing receipt at the point of action. It shows:

- **For:** Maya Chen, Aperture House
- **Purpose:** the operator's selected Claude job
- **Audience:** Private operator handoff
- **Freshness:** the exact synthetic fixture time
- **Available until:** the exact synthetic expiry
- **Included:** at least three selected source references, using their exact fixture labels
- **Current read:** The team misses early quality signals
- **Open question:** What is the first warning sign Maya notices?
- **Excluded:** at least one exact fixture item, with the reason stated, including any operator-private content outside the selected purpose

The initial packing receipt shows labels and short reasons, not raw private contents. **Inspect selection** opens the existing dialog pattern for exact source text, relationship, attribution and exclusion detail. Closing it returns to the same place on the thread.

One primary action sits directly beneath the receipt: **Make available to Claude**. Nothing crosses the boundary before this action.

### D. Hand to Claude

After the deliberate handoff, the thread gains a mint custody mark: **Available to Claude for this job**. The verdict sits where Krish acted and states exactly what happened:

**Claude can read the selected Maya context until the stated expiry. The rest of Maya's Brain and all excluded private material remain unavailable.**

The read-only connector exposes only this purpose-bound selection. It cannot alter the Brain or return material automatically.

The next primary action is **Copy task starter**. The clipboard receives only a short human-readable instruction that names the job and points Claude to the prepared handoff. It does not contain the selected Brain material, private notes, hidden schema, access language or a whole-Brain export.

If Claude access is unavailable, the handoff remains safely staged. The surface says so plainly and offers one recovery action: **Download selected context**. This is an explicit manual export of the exact inspected selection. The unavailable route is not presented as a working Claude control.

### E. Return from Claude

The read-only connector cannot write back. When Krish has a useful Claude result, he chooses **Bring back a result** on the same thread. The surface presents one focused inbound plate: **Paste Claude's result here.**

One paste creates a return receipt with:

- **Source:** Claude suggestion
- **For:** Maya Chen, Aperture House
- **Related job:** the exact outbound purpose
- **Received:** exact time
- **Status:** Private staging, not Brain memory
- **Original context:** the outbound handoff receipt remains linked and inspectable

The result is not merged with Maya's words, Krish's judgement or CTRL synthesis. The receipt keeps four attribution labels available wherever those materials meet:

- **Maya's words**
- **Krish's judgement**
- **CTRL synthesis**
- **Claude suggestion**

The final mint mark says **Returned to staging**. One next action appears beside it: **Review in CTRL later**. In the synthetic proof this action closes the exchange and returns to the Decision Bench with a visible staged-source count. It does not open or imply a trusted-memory approval workflow.

## 4. Primary interaction

The primary interaction is **handing one parcel forward on a continuous custody thread**.

The operator never chats with CTRL. Each state presents one object, one boundary and one primary action. The action changes custody or purpose, and the receipt appears beside that action immediately.

The same interaction grammar repeats without becoming a wizard:

- Place material on the thread.
- Read the immediate receipt.
- Name the Claude job.
- Inspect and approve the small handoff.
- Copy the task starter.
- Paste one result back onto the inbound segment.

There are no numbered progress steps, completion percentage or course-like sequence. The line represents custody, not achievement. Krish can close the surface after any completed receipt and resume from that receipt later in the proof state.

## 5. Information structure

### Persistent identity band

The narrow top band always shows:

- active customer and company;
- private operator or customer-visible audience state;
- current Decision Bench decision;
- freshness or source-safety warning;
- close action back to the Decision Bench.

Changing the active customer while a parcel is open never silently relabels it. The thread retains the customer fixed at capture time and closes safely on mismatch.

### Thread field

The centre of the surface contains the single horizontal thread on desktop and vertical thread on mobile. It includes:

- the current parcel;
- the active custody mark;
- previous receipts as inspectable marks;
- the one current ask or action;
- an inline answer, receipt or failure directly beside that action.

The thread field does not show a feed. Only one parcel is active. Earlier transfers are not stacked as messages.

### Context edge

The approved Decision Bench remains partially visible as context, not as a competing workspace. Its current decision and supported read feed the packing receipt. The Living Brain is available through **Inspect selection**, where each selected source can expose its typed, directed relationship to the current read. No graph is copied into the handoff surface and no new relationship is inferred.

### Receipt detail dialog

The existing dialog pattern carries exact details that would overload the thread:

- original source;
- exact included and excluded fixture references;
- source freshness;
- attribution;
- audience;
- expiry;
- typed and directed Brain relationship where one exists.

It has no nested scroll region. On small screens it becomes a natural-height page layer. Technical identifiers are hidden by default and appear only under **Technical details** for deliberate inspection.

## 6. Desktop behaviour

At 1440 by 900, the surface attaches to the Decision Bench as a no-scroll working layer rather than replacing it with a full-page tool.

- **Icon shell:** the existing icon-only shell stays fixed at the left.
- **Identity band:** 64 px high across the available width.
- **Decision context edge:** a quiet 300 px region retains Maya's current decision, supported read and open question.
- **Thread field:** the remaining width carries one continuous horizontal line with the current parcel centred in the working area.
- **Receipt area:** the active receipt expands below or beside the parcel, using available width rather than stacking cards.
- **Action position:** the primary action and its result share one local region. The result never appears at the far end of the screen.

The full representative loop fits one state at a time without page scrolling. Exact source detail may open in a dialog or page layer, but no component contains its own scrollbar. Long material is summarised only in the receipt and remains exact in deliberate source inspection.

The thread moves a short distance when custody changes. Reduced motion replaces movement with an immediate line-state and label change. Motion never carries meaning alone.

## 7. Mobile behaviour

At 390 by 844 and 320 by 568, the thread turns vertical. The same custody model and wording remain.

The sticky identity band shows **Maya Chen**, **Private**, and a short decision label. The current parcel sits directly below it. Only the active receipt is expanded. Previous receipts collapse to labelled line marks such as **Received privately** and **Made available to Claude**. Tapping a mark opens its natural-height detail and **Back to thread** restores the same point.

The paste plate receives focus only after Krish opens the exchange, so the mobile keyboard does not cover the decision context unexpectedly. File and voice alternatives remain visible below the paste instruction as equal input methods for the same ask. Each control is at least 44 px high. No gesture is required. Touch, keyboard and visible buttons complete every path.

At 200 percent zoom, desktop follows this same single-column order. Normal page movement is allowed. There is no horizontal scrolling, fixed action covering content or nested scrolling.

## 8. Knowing what happened

The concept uses receipts rather than success toasts because each receipt preserves scope and custody.

### What CTRL captured

The first receipt shows the original source type, active customer, exact capture time, private staging status, supported interpretation and explicit non-assumptions. The original remains inspectable. If CTRL understood nothing beyond the source type, the receipt says **No meaning assumed**.

### What Claude receives

The packing receipt shows the named purpose, customer, audience, freshness, expiry, exact selected fixture references and at least one explicit exclusion. After handoff, the same receipt gains a completed custody mark. It never collapses to vague copy such as **Context shared**.

### What came back

The return receipt says **Claude suggestion**, names the related purpose and keeps the result in private staging. Any nearby Brain or source material retains its own attribution label. The interface never turns a Claude sentence into Maya's words, CTRL synthesis or trusted memory through layout, colour or omission.

## 9. Required state coverage

| Required state | Thread behaviour | Primary ask or recovery |
|---|---|---|
| Ready to capture | Empty parcel position, Maya identity fixed, paste plate focused, private default stated | Paste one thing, with file and voice as alternate paths |
| Pasted material received | Immediate receipt preserves original, source type, customer, time, private status and non-assumptions | Use this in Claude |
| Ambiguity genuinely needs one answer | Amber knot stops the line after the source is safe. It asks only about the subject, audience, provenance or meaning ambiguity that changes handling | One plain choice, then continue |
| Duplicate source | Receipt says the exact source is already in Maya's private staging and shows the earlier capture time | Use the existing source |
| Processing delayed but source safe | Parcel remains at **Held privately**. The original is inspectable and the delayed interpretation is labelled pending | Continue with the original |
| Ready to use in Claude | Packing receipt shows purpose, audience, freshness, expiry, three or more exact source references and one exclusion | Make available to Claude |
| Operator-private content excluded | Exclusion line states the exact private fixture item and why it is outside this handoff. It is not selectable from the normal packing receipt | Continue with the inspected selection |
| Copied task starter | Clipboard receipt displays the exact short starter and states that no Brain contents were copied | Bring back a result |
| Claude unavailable fallback | Existing handoff remains private and intact. Claude access is labelled unavailable | Download selected context |
| Returned Claude result in staging | Return receipt identifies Claude, related purpose, capture time and `Private staging, not Brain memory` | Review in CTRL later |
| Wrong-customer failure | If the active customer differs from the parcel customer, the line closes before capture or handoff. Typed or pasted material stays in temporary local input and is attached to no Brain | Switch back to Maya |
| Expired-context failure | The connector returns no selected context. CTRL staging and the prior receipt remain intact. The expired handoff cannot be reopened as current | Prepare a new handoff |

Only one primary ask or recovery appears in each state. Secondary detail inspection never advances custody.

## 10. Failure and recovery rules

Failure closes the boundary before offering recovery.

- **Wrong customer:** stop before any association or handoff. Keep the user's current input in temporary view state. Show both customer names in plain language and offer **Switch back to Maya**. Do not offer an override in the same state.
- **Expired handoff:** share nothing. Keep the source and selection receipt in private staging. Offer **Prepare a new handoff** so freshness and expiry are reviewed again.
- **Connector unavailable:** keep the prepared selection private. Offer explicit manual download. Do not copy private contents automatically.
- **Clipboard failure:** leave the exact task starter visible and offer **Select starter** as the one recovery action.
- **Delayed processing:** preserve the source and allow work from the original. Do not generate a summary to fill the delay.
- **Duplicate:** point to the existing receipt. Do not silently create a second durable source.
- **Source error:** preserve the submitted text, URL, file name or recording in private staging when the browser has actually captured it. If capture itself failed, say that the source was not saved and keep the input visible for retry.

No error state changes customer, audience, source attribution, trusted status or Brain memory.

## 11. Implementation feasibility

The concept is a state-machine projection over the capabilities named in the sanitized brief.

### Existing React Decision Bench

The thread mounts as an attached work layer inside the current operator environment. It consumes the active-customer identity, current decision, supported read and open question already present in the Decision Bench. It does not replace the Bench, add navigation or create a second customer selector.

### Synthetic fixture

The representative proof uses fixed Maya Chen material and deterministic branches for receive, ambiguity, duplicate, delay, exclusion, expiry, mismatch and return. The three selected references and one exclusion must come from exact fixture records. If the fixture cannot supply them, the representative state fails visibly rather than inventing references.

The proof may hold the current thread in React view state or the existing proof-state mechanism. That persistence demonstrates navigation and recovery only. It is not a production staging store.

### Existing dialogs

Receipt inspection, source detail and the exact packing list reuse the current dialog behaviour. No new administration surface is required. The visible daily interaction contains no MCP, schema, token, resource or connector configuration language.

### Read-only MCP substrate

The outbound handoff maps to one read-only, purpose-bound resource assembled from the selected fixture references. Claude may read that resource until expiry. It receives no whole-Brain endpoint and no write tool. The return path is manual paste or explicit file input, which creates a Claude-attributed staging receipt. There is no automatic conversation sync or connector write-back.

The synthetic proof can deterministically show the exact resource payload, availability state and expiry result without claiming that a production connector exists. A working clipboard action copies the small task starter. A manual export action downloads only the selection Krish has inspected and explicitly chosen.

### Input paths

- Paste is a native paste event into the focused receiving plate.
- URL capture is the same text path and makes no fetching claim unless the existing proof fixture already contains the resolved source.
- File uses a working local file input and records only metadata or fixture content the proof can actually read.
- Voice is active only where a working browser capture path is implemented. Otherwise the visible option says **Voice unavailable in this proof** and is not styled as a control.

No active control depends on a production account, external write, unimplemented inference or unavailable connector action.

## 12. Hard-failure audit

| Hard failure | How this concept prevents it |
|---|---|
| Whole-Brain or vague automatic context sharing | One named purpose creates a small inspectable selection. The exact inclusions and exclusions are shown before handoff. Nothing is selected or sent automatically. |
| Trusted-memory write-back | Every inbound Claude result is labelled `Claude suggestion` and `Private staging, not Brain memory`. Review is a later governed action outside this surface. |
| Unclear active customer | Maya's identity and company remain in the fixed identity band and on every receipt. Customer mismatch closes the route before transfer. |
| Technical setup as the daily experience | The daily object is a parcel on a custody thread. Connector and resource details are hidden behind deliberate technical inspection. |
| More than one primary ask per state | Each state has one ask or recovery. Alternate input methods answer the same capture ask. Detail inspection does not advance the thread. |
| Generic upload or chat UI | The governing object is a receipted context parcel whose custody, audience, purpose and truth status change along one continuous route. There is no transcript, assistant turn, generic file queue or modal-only flow. |
| Active-looking control that cannot work | The proof renders only working paste, file, clipboard, dialog, selection, download and state-transition controls. Voice and connector actions are disabled or absent when unavailable. |
| Unsupported product claims | Every representative value comes from the synthetic brief or exact fixture. The proof states that it demonstrates transfer mechanics only and proves no diagnostic quality or customer value. |

## 13. Why this is not a conventional shell

It is not an upload modal because capture is only the first custody mark. The same object remains visible while its purpose, audience, selection, expiry and return attribution change. A generic uploader loses that continuity as soon as the file is accepted.

It is not chat because there is no transcript, composer, assistant persona, streaming answer or alternating turn structure. The user advances a context parcel across explicit authority boundaries and reads receipts at those boundaries.

It is not a settings integration page because there are no connectors to configure, permissions to administer or accounts to manage in the daily surface. Claude appears as one read-only destination for one job, not as an installed service tile.

It is not a course or wizard because the thread measures custody, not progress. There are no numbered steps, percentage, completion reward or mandatory tour. A completed receipt is a safe stopping point.

It fits the Decision Bench because the current decision supplies the purpose and the Living Brain supplies inspectable evidence relationships. The exchange does not become a second truth store or a detached utility.

## 14. Strongest failure risk and kill test

The strongest risk is that the thread becomes a decorative progress line wrapped around an ordinary paste-and-export flow. If the active customer, purpose, exact selection, exclusion and attribution are not legible at the moment custody changes, the metaphor has done no product work.

The render should be killed if a cold user cannot answer these four questions after one representative handoff:

1. Which customer is this for?
2. What exactly can Claude see, and until when?
3. What stayed out?
4. Did the returned result become Brain memory?

The call is to keep one parcel and one custody thread on the surface. The sharper alternative is to remove almost all path history and show only the current and immediately previous receipt, but that trades away some audit clarity. The next action is independent concept judgment before any rendering. The main counterpoint is that a continuous path can resemble onboarding if custody labels are vague or numbered. The concept therefore depends on literal receipts and boundary language, not a visual stepper.
