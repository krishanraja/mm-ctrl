# G22 concept spine: The Consequence File

**Concept revision:** C1  
**Source boundary:** G22 sanitized brief R1 only  
**Status:** Independent concept for judging, not an implementation lock

## The call

Build the proof as one living case file whose current edge moves forward when a real consequence is recorded.

The file begins with work already done, not an empty prompt. CTRL notices a decision inside that work, gathers only the evidence needed to make it useful, and asks Maya one question only if her answer changes the route. Her call becomes a dated event. A proposed learning follows it. Maya can accept it, correct it or reject it. When she returns later, the file shows exactly where an accepted learning changed the new preparation. The final release is a version of this same governed record, not a separate export experience.

The organising metaphor is a consequential thread across time. It should feel closer to opening the current case on a desk than entering a dashboard.

## Design contract

**State of use:** An advisor works on a laptop between sessions. Maya receives a small number of one-handed phone moments. Either may return after several days with no memory of the interface.

**User and action:** The advisor must see what deserves attention and why. Maya must make the few calls only she can make. Both must understand how one earlier judgement affects later work.

**Governing rule:** The Brain is the single record. Every view is a projection of dated events, sources, standing, uncertainty, dependencies and ownership.

**Data truth:** All records are deterministic synthetic fixtures. Every claim carries an origin label. Demonstration evidence proves the interaction mechanic only.

**Materiality:** Material concept. The temporal interaction, information model and responsive behaviour require approval before implementation.

**Authority:** Draft concept only. It does not approve a rendered surface, implementation, production navigation, release or external action.

**Proof target:** Representative, quiet, sparse, stale, proposed, accepted, corrected, rejected and later-return states at wide desktop and narrow phone widths.

## Primary interaction: move the current edge

The product has one persistent **case thread** and one **current edge**.

The case thread is a compact dated index of consequential moments. It is always available. It is not a progress bar. Past moments remain selectable and keep their original wording, source state and outcome. Unreached future moments do not appear as locked steps. The current edge is the latest event that needs judgement or can change what follows.

Selecting a moment replaces the single work region. The shell does not open several competing panels. Each current-edge view contains:

1. what changed;
2. why it matters now;
3. the minimum evidence behind it;
4. one action, question or decision group; and
5. the result directly beneath the action.

The user never presses **Next**. Actions create events. New events move the current edge.

### The eight-action ceiling

The complete representative case uses eight primary action types. Alternative outcomes inside one decision group do not create extra stages.

| # | Primary action | Actor | Event created |
|---|---|---|---|
| 1 | Inspect the source bundle | Advisor | `bundle_opened` |
| 2 | Answer the route-changing question | Maya | `route_answered` |
| 3 | Open the decision table | Advisor | `decision_work_started` |
| 4 | Record the call and first gate | Maya with advisor | `decision_recorded` |
| 5 | Resolve the proposed learning: accept, correct or reject | Maya | `learning_resolved` |
| 6 | Open the later preparation | Advisor | `return_opened` |
| 7 | Set the final standard | Maya | `standard_recorded` |
| 8 | Approve and take away the release | Maya with advisor | `release_approved` and local download |

Opening a source label, inspecting history, moving between existing moments and closing a drawer are secondary inspection controls. They do not advance the case.

## The five moments in the file

### 1. Arrival: work becomes a case

The file opens on a dated intake sheet assembled from natural work residue and deliberate input. It preserves four fields at the top:

- source;
- subject;
- purpose; and
- audience.

The visible lead is not “content ingested”. It is the consequence CTRL can now see.

Example:

> A marketing decision now affects £1.2m and eight roles.
>
> Company work · Demonstration fixture

Under it, a short source bundle shows the useful tension:

- Maya judges alternatives comparatively, not by a fixed score.
- Her standard is to make quality clear without killing surprise.
- The current volume scorecard rewards the wrong thing.
- Customers value a clear point of view more than more output.
- It is not yet clear whether Maya’s quality standard can travel without her final rescue.

Each line has one of five explicit origins: **Maya**, **Customer evidence**, **Company work**, **Public research** or **CTRL proposal**. Origin is text plus a distinct line mark, never colour alone.

The current-edge statement is:

> This is a decision, not a content task.

The advisor can inspect the source bundle. If the evidence does not earn an interruption, Arrival remains quiet and no later moment appears.

### 2. Decision: earn the deeper instrument

The Decision moment appears only when the deterministic case rules have all of the following:

- a consequential subject;
- named budget or role exposure;
- at least two source classes;
- a tension that changes an operating choice; and
- a recorded uncertainty level.

Before the rich instrument opens, the work region shows one compact decision cover:

> How far should Aperture House rebuild marketing around AI?

It includes **Why now**, **What Maya sees differently** and **What is still unknown**. These are three short evidence-backed lines, not summary cards.

If the unresolved question changes which route is sensible, the leader receives one phone prompt:

> Can your quality standard travel without your final rescue?

Response choices:

- Yes, with a clear review rule
- Not yet
- I need to test it

A voice or one-sentence note is available but optional. The response lands under the choices:

> Recorded. The decision now treats delegation as a test, not an assumption.

Only then does **Open decision table** become available.

### The approved Decision Table as one earned state

The existing R4 Decision Table is embedded unchanged as the decision workpaper. This concept does not alter its columns, scoring logic, controls, density or visual hierarchy.

The shell contributes only a narrow case-file frame:

- the decision title and date;
- a plain **Ready** status;
- the evidence snapshot version used by the table;
- an inline route answer, if one was required;
- source and history inspection; and
- a return control to the case thread.

On wide desktop, opening the table temporarily reduces the temporal index to a slim dated rail so the approved organ receives the available width. Completing its existing decision action writes a `decision_recorded` event back to the case file. The result appears beside or directly under the action in the table’s existing result area, then the case returns to its normal width.

On a narrow phone, the dense table is not squeezed, horizontally scrolled or reinvented. The phone shows the decision cover, Maya’s immediate question or gate, and this honest handoff:

> The full decision table needs a larger screen.

The leader can still answer the route-changing question and later confirm the recorded call on the phone. The operator instrument remains a desktop state.

### 3. Learning: a proposal, not a fact

After the call, CTRL proposes one learning derived from Maya’s reasoning. It appears as a loose amendment sheet attached to the Decision moment, visually incomplete until Maya resolves it.

Example:

> Proposed learning
>
> Maya will delegate AI-assisted marketing work when the review rule protects surprise as well as clarity.
>
> CTRL proposal, based on Maya’s recorded call

The only primary decision group is:

- Accept
- Correct
- Reject

The result appears in place.

**Accept** changes the sheet to **Accepted for later work**, records who accepted it and when, and makes it eligible to influence later preparation.

**Correct** opens one focused correction field with voice first and typing as fallback. The original proposal remains visible in history. The corrected learning receives a new version and a link reading **Changed because Maya corrected it**.

**Reject** records the rejection and removes the proposal from active reasoning. The record remains inspectable and cannot influence later work.

### 4. Later return: prove that the file learned

The return moment is a new dated event, not a replay of the decision. It opens on a useful preparation whose difference can be traced to the accepted or corrected learning.

The signature comparison is one compact **before / because / now** strip:

| Before | Because | Now |
|---|---|---|
| The preparation treated delegation as a general risk. | Maya accepted a review rule that protects clarity and surprise. | The preparation asks whether the review rule worked without Maya’s final rescue. |

The centre cell links back to the exact learning version. Selecting it opens the dated amendment and its source chain without leaving the current work.

This strip is the core proof of compounding value. It does not claim that CTRL improved company performance. It shows that a later preparation uses a piece of accepted personal judgement that did not exist in ordinary context.

If the learning was rejected, the strip explicitly says:

> The rejected proposal was not used.

If it was corrected after the later preparation was first created, the preparation shows **Needs refresh** and presents the affected sentence before any new version replaces it.

### 5. Ownership: release a version of the same record

Ownership is the last dated event, not a settings page. The work region shows what will leave the live Brain and who owns each part.

The release sheet separates:

- Maya’s personal judgement;
- Aperture House company material;
- public research references;
- CTRL proposals and their resolution;
- correction history; and
- the decision and later-use links.

Maya first records the final standard in one sentence or by voice. She then approves the release. The local proof creates a deterministic ZIP download and a matching manifest view. No account, repository or message is created.

Example:

> Ready to take away
>
> Living Brain version 1.3 · Synthetic case

The result appears under **Approve release**:

> Approved by Maya. Your ZIP is ready.

The ZIP control is enabled only after approval. A future GitHub route may sit in the product model, but it is absent or plainly unavailable in this unlinked proof.

## Information structure

### Persistent shell

The shell contains only:

1. **Case identity:** Maya Chen, Aperture House, 30-day proof.
2. **Current status:** Quiet, Needs judgement, Waiting for Maya, Learning proposed, Needs refresh or Ready to release.
3. **Temporal case thread:** only moments that exist, each with date, state and one-line consequence.
4. **Single work region:** the selected moment.
5. **Ownership access:** source, version and release history through one inspection drawer.

There is no global feature navigation inside the proof. Feed, audio, research, decision, Brain and export do not appear as separate destinations. Their outputs enter the case as evidence or events.

### Work-region reading order

Every moment uses the same reading order:

1. plain consequence;
2. status and date;
3. evidence or prior event that earned it;
4. one action area;
5. immediate result;
6. optional history and sources.

This constant frame lets the content become more sophisticated without making the interface harder to learn.

### Provenance grammar

Every claim line carries a compact origin label and an inspectable source record. Five line-end marks provide a non-colour cue:

- short vertical line: Maya;
- double line: Customer evidence;
- square: Company work;
- open circle: Public research;
- corner bracket: CTRL proposal.

Standing appears next to origin when it changes action: **Current**, **Stale**, **Proposed**, **Accepted**, **Corrected** or **Rejected**. Timestamps stay in the source drawer unless freshness affects the decision.

## State model

The implementation should use an append-only event log plus derived projections. A correction adds an event. It never edits the earlier event in place.

### Core case state

```text
case.status
  quiet | needs_judgement | waiting_for_maya | learning_proposed |
  needs_refresh | ready_to_release | released

case.activeMoment
  arrival | decision | learning | return | ownership

evidence.coverage
  representative | sparse | stale

decision.status
  detected | question_required | ready | recorded

learning.status
  none | proposed | accepted | corrected | rejected

return.status
  unavailable | prepared | opened | needs_refresh

release.status
  unavailable | ready | approved | downloaded
```

### Transition rules

| Current event | User action or rule | New event | Visible consequence |
|---|---|---|---|
| Residue recorded | Decision threshold not met | None | Quiet case, no interruption |
| Residue recorded | Decision threshold met | `decision_detected` | Decision moment appears |
| Decision detected | Route answer required | `question_requested` | One Maya prompt appears |
| Question requested | Maya responds | `route_answered` | Table becomes ready |
| Decision ready | Existing table records call | `decision_recorded` | Call and first gate appear in thread |
| Decision recorded | CTRL derives candidate | `learning_proposed` | Amendment awaits Maya |
| Learning proposed | Maya accepts | `learning_accepted` | Version becomes active |
| Learning proposed | Maya corrects | `learning_corrected` | New version becomes active, old one remains |
| Learning proposed | Maya rejects | `learning_rejected` | Proposal becomes inactive |
| Later work arrives | Active learning is relevant | `return_prepared` | Before / because / now strip appears |
| Active learning changes | Existing return depends on it | `return_invalidated` | Later preparation shows Needs refresh |
| Final standard recorded | Release contents valid | `release_ready` | Approval becomes available |
| Maya approves | Local package generated | `release_approved` | ZIP becomes available |

### Dependency repair

Each derived claim stores `dependsOnEventIds`. When a learning is corrected or rejected, the selector identifies every current projection that depends on the superseded event.

Affected outputs change to **Needs refresh**. The interface first shows what was affected, then lets the deterministic fixture generate the corrected version. The history retains:

- the old output;
- the proposal it used;
- Maya’s correction or rejection;
- the regenerated output; and
- the current active version.

No history is erased. No rejected learning remains active. No corrected output silently pretends it was always right.

## Desktop choreography

At a wide viewport, the case identity and status sit in a restrained top bar. A 240 to 280 pixel temporal index occupies the left edge. The work region uses the remaining width with a readable maximum line length. There is no permanent right sidebar.

The index is chronological but not evenly segmented. Each moment takes only the height its event needs. The current edge uses a quiet amber rule and date. Accepted knowledge uses mint only at the exact accepted statement. Past events use paper and ink contrast. Source marks carry provenance.

The selected sheet enters with a short vertical settling motion, like a new page placed on the same file. Correction adds a thin replacement sheet over the prior edge while leaving the older edge visible behind it. Reduced-motion mode removes translation and uses an instant border and status change.

Sources and history open in a drawer over the work region, not as a nested scrolling panel. The page owns vertical scroll. Closing the drawer returns focus to the claim that opened it.

When the Decision Table opens, the left index compacts to dates and status marks. The table receives the full working width. Leaving the table restores the normal index without losing table state.

## Mobile choreography

At a narrow viewport, the case identity becomes a two-line header. The temporal index becomes a horizontally scrollable strip of existing dated moments. It is labelled **Case history**, never **Progress**. The selected moment is announced to assistive technology and brought into view without trapping horizontal page movement.

The work region becomes one full-width sheet. It contains one immediate action or decision group. The action stays near the content that explains it, not in a detached global footer. Source labels open a full-height bottom sheet with a clear close control and focus return.

Mobile moments are deliberately sparse:

- answer one route-changing question;
- accept, correct or reject one learning;
- record one final standard;
- approve one release.

Voice appears beside the one-sentence fallback. Any draft response persists across close, rotation and reload. Autosave status appears once beside the input. Touch targets remain comfortably tappable, the keyboard cannot cover the result, and safe-area padding keeps the final control reachable.

The phone never attempts to administer sources, inspect the full Decision Table or configure the Brain.

## Meaningful visual system

The visual language is a modern governed case file, not courtroom theatre and not skeuomorphic office stationery.

- **Ground:** deep ink green shell with warm paper work sheets.
- **Signal colour:** amber marks the current edge or a changed dependency. Mint marks an accepted answer only.
- **Type roles:** structured sans for headings, readable serif for the consequential claim, monospace for dates, versions, origins and controls.
- **Case thread:** one fine temporal rule. Its nodes are events, not feature icons.
- **Layered edges:** one or two visible sheet edges show that a correction created a new version. They correspond to real versions and disappear when there is only one.
- **Source marks:** five simple line shapes encode origin with text labels.
- **Dependency trace:** selecting **Used here** draws one short animated line from the accepted learning to the changed sentence in the later preparation. It appears only on request and carries both endpoint labels.
- **Motion:** page settling, current-edge movement and dependency repair only. No particles, sparkle, celebration, pulsing status or decorative graph movement.

The strongest visual is the causal join between an accepted learning and a later changed sentence. If that link does not carry real event IDs, remove it.

## Range handling

### Quiet or no-earned-interruption

The file opens on Arrival with:

> Nothing needs Maya now.

The advisor can inspect what arrived. No red badge, empty chart, recommendation or future moment appears. Quiet is a successful state.

### Sparse evidence

When the decision threshold lacks two independent source classes or a named consequence, CTRL does not infer a rich decision. It shows what is present, what is missing and one route-changing request only if a single answer can close the gap.

Example:

> We can see the budget. We cannot yet see what customers would lose.

If the missing evidence cannot be recovered inside the proof, the action is **Leave this open**. The Decision Table remains unavailable.

### Stale evidence

Staleness appears on the exact claim it affects. A stale budget or customer signal changes the current edge to **Check before deciding**. The table may be inspected. The existing call action changes to a qualified choice: **Record with stale evidence** or **Leave this open**.

If the call is recorded, its decision record is visibly qualified. The proof never refreshes a source silently or invents a current replacement.

### Proposed learning

The proposal uses an open corner bracket and neutral paper. It cannot affect later work. The current status is **Waiting for Maya**.

### Corrected learning

The original and correction remain as two dated versions. Only the corrected version is active. Every dependent later output receives **Needs refresh** until regenerated.

### Rejected learning

The proposal remains in history with a plain **Rejected by Maya** label. It cannot be selected as current knowledge and cannot appear in the causal join. Later work may state that it was excluded.

### Long or adversarial input

Visible excerpts cap by meaning, not by fixed character clipping. The source drawer shows the full synthetic text in natural page flow. Untrusted source text never supplies interface labels, event types or action names.

### Loading and error

The proof is local, so loading should be brief but truthful. A sheet skeleton may reserve layout for fixture hydration. If local state fails, keep the user’s pending answer in memory and show **Could not save. Try again.** beside the action. No success state appears until the event exists in the log.

## Why this is not a tour or e-learning sequence

- Time is the product state, not a sequence of slides.
- There is no percentage, step count, lesson, checkpoint, completion score or Next control.
- Past moments remain open and can be inspected in any order.
- Future moments do not exist until a source, decision or judgement creates them.
- Maya’s acceptance, correction or rejection changes which later preparation can be produced.
- Quiet, sparse and stale cases can stop without “finishing”.
- The case can reopen after days because the current edge comes from the event log, not session progress.
- The Decision Table is a work instrument inside the case, not a lesson about a feature.
- Ownership ends in a portable governed version, not a congratulations screen.

The chronology demonstrates causality. It does not teach the user how to click through CTRL.

## Feasible implementation boundary

This concept can run as one deterministic local route with:

- one fixture package;
- an append-only in-memory or approved local persistent event store;
- one reducer for the transition rules;
- selectors for current standing, active moment, stale dependencies and release contents;
- a persistent shell and one swapping work region;
- the approved R4 Decision Table mounted as a black-box organ with an input snapshot and a decision-event output;
- local voice capture where supported, with tap and text fallback;
- a client-side ZIP generated from the active governed projection plus history manifest;
- a non-indexable document head and no external requests.

The proof makes no database write, model call, message, account, repository or production-navigation change. Every visible control either changes the local event state, opens inspectable evidence, returns focus, or downloads the approved local package.

## Success signal and kill conditions

The concept passes only if a fresh observer can answer these five questions after one representative run:

1. What work entered the Brain?
2. Why did CTRL interrupt Maya?
3. Which part of the decision depended on Maya specifically?
4. What changed in later work because of an accepted or corrected learning?
5. What does Maya own and take away?

Kill the concept if the observer describes it as a timeline tour, if the later preparation would be identical after rejection, if any claim lacks an origin, if the Decision Table appears as the home screen, if the phone tries to reproduce desktop density, or if a correction rewrites history.

## Sharper alternative

A sharper version removes the five named moment labels and lets the dated case thread grow from event titles alone. That would feel even less like a staged proof, but it would raise first-use comprehension risk. Keep the five plain moment labels for C1, then test whether observers use them to understand causality or mistake them for steps.

## Next move

Render only the representative accepted path at wide desktop and the route-changing Maya prompt at narrow phone width. Show it cold. If the founder reads the left rail as progress, reject the temporal spine before adding more states.
