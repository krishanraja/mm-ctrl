## Purpose

## One operation-result authority

There is one operation registry keyed by exact workspace and operation ID. Its versioned committed-success row owns principal, case scope, request identity, canonical result bytes, result schema, result fingerprint and any branch-specific result reference.

Release terminal consumption uses that canonical row directly. Each successful branch declares its exact schema, result-reference field, complete fingerprint preimage and terminal receipt field. Pending delivery can resolve only through its Release-use receipt; invalidation can resolve only through its invalidation receipt. A second operation-result registry or a parallel `operation_ref` namespace is invalid.

## One lifecycle vocabulary

Every active lifecycle structure uses the authoritative receipt vocabulary. Nullable predecessor identity is `predecessor_lifecycle_version_ref`; actions are identified by action receipt reference and fingerprint; combined authority is identified by authority receipt reference and fingerprint.

The combine intent, nonce collision rules, pair collision rules and transition predicates use those same fields. The four obsolete standalone lifecycle fingerprint schemas are removed because the authoritative row families already own the semantic fingerprints. The machine contract declares every active lifecycle root and rejects any legacy token within one.

## One owner after worker death

Final provider rechecks remain an ordered first-match decision over one serializable snapshot. When the invocation tip is still current, the lease has expired and a capability was consumed or a provider call may have begun, the lease reaper must append lease-expiry ambiguity before any worker or no-call-abort path can match.

Live-worker ambiguity is limited to a live lease. A proven unconsumed expired invocation may still take the reaper's no-call abort path. Every append requires compare-and-swap against the same current-tip snapshot.

## Visible experience

Nothing in R15 adds visible ceremony. The internal registry, receipt, fingerprint and recovery machinery must remain behind one natural question, answer or Release action. It exists to make a deceptively simple experience truthful under replay, expiry and failure.
